**What actually failed in the six NCCL jobs.** The first NCCL communicator
*did* initialise successfully over IBext_v11 (`NET/IB : Using mlx5_0:1/IB/SHARP …`)
and the first `all_reduce` ran (`last completed work: 1`). The hang occurs on
the *second* collective when PyTorch lazily creates a per-(process-group, cudaDev)
sub-communicator. Across the failed runs the cudaDev mapping is asymmetric:

| run             | node-0 ranks → cudaDev | node-1 ranks → cudaDev | symmetric? |
|-----------------|------------------------|------------------------|:---------:|
| 2×1 a0004-9643  | rank 0 → 0             | rank 1 → **1**         |     ❌    |
| 2×2 a0006-9644  | ranks 0,1 → 0,1        | ranks 2,3 → **2,3**    |     ❌    |
| 2×4 a0008-9645  | ranks 0..3 → 0..3      | ranks 4..7 → **4..7**  |     ❌    |
| 2×8 a0010-9646 ✅| ranks 0..7 → 0..7      | ranks 8..15 → **0..7** |     ✅    |

The launcher selects `cudaDev = global_rank % torch.cuda.device_count()`, and
inside the Apptainer container `device_count()` is **8 regardless of Slurm's
GPU allocation** because `APPTAINERENV_CUDA_VISIBLE_DEVICES` from
`SLURM_JOB_GPUS` is not filtering devices down on these jobs (the cluster's
known cgroup-isolation gap). Therefore:

- `world_size ≥ 8` (the 2×8 case): `rank % 8` collapses node-1 ranks back to
  `0..7`, so both nodes use matching cudaDev indices → symmetric → NCCL is
  happy.
- `world_size < 8` (the 1, 2, or 4 GPUs/node cases): every rank gets a
  *unique* cudaDev across the job → node-0 uses `0..N-1`, node-1 uses
  `N..2N-1` → asymmetric.

PyTorch's NCCL backend keys its lazy sub-communicators by cudaDev.
On the second collective, rank 0 publishes its `ncclUniqueId` under key
`…/cuda/0`, but a rank on the other node looks for `…/cuda/<its own cudaDev>`,
which rank 0 never wrote — `c10d::ProcessGroupNCCL::broadcastUniqueNCCLID`
times out after 600 s and the job dies. So the failure is *not* an IB issue
and *not* a c10d-rendezvous issue — it's a launcher device-pinning bug
exposed by partial-node allocations.

**Fixes (either is sufficient):**

1. Pin the device by `LOCAL_RANK` in the training script
   (`torch.cuda.set_device(int(os.environ["LOCAL_RANK"]))`). With
   `torchrun --nproc_per_node=$N_GPUS`, `LOCAL_RANK` is `0..N_GPUS-1` on every
   node, so cudaDev assignment is automatically symmetric.
2. Make `APPTAINERENV_CUDA_VISIBLE_DEVICES=$SLURM_JOB_GPUS` actually
   propagate into the container for partial-node allocations. Then
   `device_count()` becomes the allocated count and the existing
   `rank % device_count` formula produces a symmetric mapping.

Doing both is the belt-and-suspenders fix; either one alone unblocks
2-node runs with fewer than 8 GPUs/node.

Per-GPU compute throughput on B200 is ~3.6× RTX 6000 in this bf16 GPT workload.
The B200 iter time at a fixed GBS of 128 is *longer* because the same GBS is
processed by a single GPU in both cases — but B200 sustains ~3.6× the FLOPs that
the model body actually exposes, indicating substantially more arithmetic per
unit time. Both single-GPU runs spend a negligible (<0.1 %) fraction in
all-grads-sync, as expected when there is no data-parallel reduction.

## Multi-node scaling

Only one valid 2-node datapoint exists per GPU type (the others timed out in
NCCL bootstrap; see "Excluded runs"):

| GPU      | 1 node × 8 GPU | 2 node × 8 GPU | Δ TFLOP/s/GPU | scaling eff. (vs 1×8) |
|----------|---------------:|---------------:|--------------:|----------------------:|
| RTX 6000 |          264.8 |          263.5 |        −0.5 % |              **99.5 %** |
| B200     |          993.3 |          978.9 |        −1.4 % |              **98.5 %** |

For both GPU types, going from 1×8 to 2×8 GPUs adds <1.5 % per-GPU throughput
loss — i.e. with full-node allocations, **inter-node DDP is essentially free at
this model size**. The all-grads-sync absolute time barely moves on RTX 6000
(427 → 412 ms — within run-to-run noise) and rises modestly on B200 (84 → 141 ms,
+56 ms), so the inter-node leg of the all-reduce on B200 costs ~60 ms per step.

The other 2-node runs (with 1, 2, or 4 GPUs/node) all hit a **600 s c10d store
timeout during NCCL communicator setup**, before any NCCL collective ran. This
is consistent with the documented cluster issue (lack of cgroup GPU isolation
on these partitions): when a node is *not* fully allocated, co-resident jobs
race for GPU 0, so two ranks of one job can land on the same physical device
or a different job's process owns the device, breaking rendezvous. The
"2 nodes × 8 GPUs/node" cases get whole nodes and therefore avoid the
collision.

## All-grads-sync time

Summary of the all-reduce (DDP gradient sync) cost across configurations:

| config            |  RTX 6000 | B200    |
|-------------------|----------:|--------:|
| 1 node × 1 GPU    |   3.7 ms  |  4.9 ms |
| 1 node × 2 GPU    | 156.6 ms  | 66.7 ms |
| 1 node × 4 GPU    | 365.2 ms  | 77.6 ms |
| 1 node × 8 GPU    | 427.7 ms  | 84.4 ms |
| 2 node × 8 GPU    | 411.9 ms  | 140.6 ms|

Two clear effects:

1. **Single-GPU baseline is tiny** (≤6 ms). It is non-zero because Megatron
   still posts the bucket reduction; with a DP world size of 1 it is just a
   no-op on local memory.
2. **B200 amortises the all-reduce ~5× better than RTX 6000 inside a node**
   (e.g. 8 GPUs: 84 ms vs 428 ms). The two GPU types share the same model
   gradient volume, so the gap is purely from the higher-bandwidth NVLink/
   NVSwitch domain on B200 versus the RTX 6000 inter-GPU fabric.
3. **Going from 1×8 → 2×8 nodes adds only ~56 ms on B200 and is within
   noise on RTX 6000**, suggesting the inter-node leg over IB is well
   pipelined with computation.

Yes — every multi-GPU run (single-node and multi-node) loaded the
**`NCCL RDMA Plugin v11`** plus the **SHARP collnet plugin** at startup, e.g.

```
NCCL INFO NET/Plugin: Loaded net plugin NCCL RDMA Plugin v11 (v11)
NCCL INFO NET/Plugin: Loaded collnet plugin SHARP (v11)
```

Both successful 2-node jobs (a0010, b0007) loaded these plugins, so inter-node
all-reduce is going over InfiniBand RDMA with SHARP available for in-network
reductions. The 2-node *failures* never reached NCCL transport selection — they
timed out in the c10d TCP key-value bootstrap (`store->get('1') ... wait timeout
after 600000 ms`), which is unrelated to IB.

## Key observations

1. **B200 delivers ~3.6× the per-GPU bf16 throughput of RTX 6000** on this 1.3 B
   GPT model (1024 vs 281 TFLOP/s/GPU at 1 GPU).
2. **Intra-node weak scaling is excellent on both platforms** (RTX 6000 ~94 %,
   B200 ~97 % at 8 GPUs). The remaining loss on RTX 6000 is almost entirely
   gradient all-reduce overhead.
3. **At full-node allocation, multi-node scaling is near-perfect** (~99 % on
   RTX 6000, ~98 % on B200) — the inter-node all-reduce over InfiniBand RDMA
   adds only ~60 ms/step on B200 and is within run-to-run noise on RTX 6000.
4. **InfiniBand + RDMA + SHARP plugins load on every multi-GPU job**, so
   inter-node communication does use IB; the failed multi-node jobs aborted
   *before* network selection.
5. **Multi-node jobs that did *not* allocate full nodes failed at NCCL
   bootstrap.** This matches the known cluster issue: with no cgroup
   `ConstrainDevices` and partial-node allocations, ranks from co-located
   jobs collide on GPU 0 and rendezvous deadlocks. Until the admins enable
   cgroup GPU isolation, multi-node sweeps should request entire nodes.
6. **Run-to-run variation on identical 1 GPU B200 configs is ~3 %** (996 vs
   1024 TFLOP/s for b0004 vs b0025); RTX 6000 single-GPU repeats are
   essentially identical (280.9 / 280.9). When comparing configs that differ
   by a few percent, this noise floor should be kept in mind.
7. **GBS scales 1:1 with total GPU count in this sweep** (per-GPU GBS = 128
   throughout). All scaling numbers are therefore weak-scaling — any iter-time
   growth is communication or pipeline overhead, not increased per-GPU work.
